# Семейный планировщик в Telegram — план реализации

## Context

Нужен Telegram-бот, который двое (муж и жена) используют как общую «внешнюю память» семьи: задачи на каждый день, заметки, списки покупок, события. Бот должен сам напоминать в нужное время, каждое утро присылать план на день, вести календарь и показывать, **кто и когда** сделал каждую запись. Проект пустой — начинаем с нуля.

**Почему пишем сами, а не форкаем.** Исследование GitHub (14 репозиториев проверено напрямую) не нашло живого проекта, закрывающего связку «общая семейная база + задачи + заметки + покупки + напоминания + дайджест + авторство». Что нашлось:
- **Donetick** (2.5k★, активен, AGPLv3) — единственный живой и близкий по смыслу, но Telegram у него только канал push-уведомлений; ввод данных — через веб/моб. приложение. Чтобы получить чат-интерфейс, бота всё равно пришлось бы писать самому, но уже поверх Go+React-сервиса.
- Все telegram-first кандидаты — либо архивированы с 2020 г. (`MasterGroosha/telegram-reminder-bot`, `grocy-telegram-bot`), либо однофункциональны (только покупки / только бюджет), либо 0–1 звезда, т.е. непроверенный код без тестов и миграций.
- No-code пути (n8n-шаблон — платный $30; Vikunja + мост; Home Assistant) требуют поднять ещё 1–2 сервиса и всё равно писать прослойку.

Объём собственной работы небольшой — 6 таблиц и один цикл-планировщик, — поэтому разбор чужого непроверенного кода не окупается. **Как референс** (подсмотреть, не форкать): схема `family_id` + участники из `parfeniukink/family-budget-bot`, UX «сообщение → инлайн-чекбоксы» из `devforth/tobedo`.

**Решения, зафиксированные пользователем:** единственный чат — общая группа «Семья»; ввод — свободный текст с разбором LLM через **OpenRouter** плюс кнопки/команды как дубль; хостинг — домашний ПК (режим работы 24/7 не определён → нужна догонка пропущенного и лёгкий переезд на VPS); голосовые распознаём в облаке; нужна интеграция с Google Календарём; Mini App — вторым этапом.

## Стек

| Слой | Выбор | Почему |
|---|---|---|
| Бот | **aiogram 3.31** (long polling) | Актуальная стабильная ветка (aiogram 4 не существует). Polling не требует публичного HTTPS — критично для домашнего ПК за NAT |
| БД | **SQLite + SQLAlchemy 2.0 async (aiosqlite) + Alembic** | Двое пользователей, сотни записей — Postgres избыточен. Один файл легко бэкапить и увезти на VPS |
| Планировщик | **свой цикл-тикер на asyncio, без APScheduler** | см. ниже |
| LLM | **OpenRouter** через `httpx` | Модель задаётся в `.env`, меняется без правки кода |
| Голос | Telegram OGG → `ffmpeg` → мультимодальная модель / Whisper-эндпоинт | Один внешний вызов вместо локальной модели |
| Упаковка | дома — **venv + Планировщик задач**, на VPS — **Docker** | Это один процесс с файлом SQLite: оркестрировать нечего, а Docker Desktop на Windows тянет WSL2 и ещё одну точку отказа в автозапуске. Dockerfile при этом пишем сразу — он окупается на VPS и на этапе 5, где нужен `ffmpeg` |

### Почему не APScheduler (важный компромисс)

Очевидный путь — APScheduler с персистентным `SQLAlchemyJobStore` (одна джоба на напоминание). Отказываемся, потому что:
- APScheduler 4 до сих пор в альфе (4.0.0a6, апрель 2025) и в документации прямо помечен «не для продакшена»; 3.x-jobstore **синхронный** и конфликтует с async-движком SQLAlchemy — лечится вторым, отдельным sync-подключением к той же БД. Лишняя сложность на ровном месте.
- Джобы сериализуются pickle — их не посмотреть глазами и не починить руками.
- Главное: при выключаемом домашнем ПК нужна **догонка пропущенного**, а `misfire_grace_time` для этого настраивается плохо.

Вместо этого — один фоновый `asyncio`-цикл (~20 строк), раз в 60 секунд:
```
due = SELECT * FROM reminders WHERE active AND sent_at IS NULL AND fire_at <= now_utc
→ отправить, проставить sent_at, для повторяемых посчитать следующий fire_at через dateutil.rrule
→ проверить, не пора ли утренний дайджест (families.last_digest_on < сегодня и время наступило)
```
Всё состояние — обычные строки в SQLite. Рестарт переживается бесплатно, догонка получается сама собой. Если позже понадобятся сложные cron-правила — APScheduler добавляется поверх без переделки данных.

**Логика догонки** (задаётся порогами в `.env`):
- опоздание < 10 мин — просто отправить;
- 10 мин … 12 ч — отправить с пометкой «⏰ было запланировано на 19:00»;
- > 12 ч (ПК был выключен ночь/сутки) — не спамить по одному, а свернуть в одно сообщение «Пока меня не было: 5 пропущенных» со списком.

## Модель данных

Всё время в БД хранится **в UTC**; таймзона семьи (`families.tz`, по умолчанию `Europe/Moscow`) применяется только на границе: при разборе ввода и при выводе. SQLite не знает про таймзоны — экономить на этом нельзя, иначе переход на летнее время и переезд на зарубежный VPS сломают напоминания.

```
families    id, title, chat_id UNIQUE, tz, digest_time ('08:00'), last_digest_on,
            listen_mode ('trigger' | 'all'), created_at
members     id, family_id, tg_user_id, display_name, joined_at        UNIQUE(family_id, tg_user_id)
lists       id, family_id, name, kind ('shopping'|'checklist'), archived, created_at
entries     id, family_id, author_id, kind ('task'|'note'|'event'|'shopping'),
            title, body, due_at, all_day, status ('open'|'done'|'archived'),
            list_id, position, assignee_id,
            source_chat_id, source_message_id,          -- ссылка на исходное сообщение
            created_at, updated_at, done_at, done_by
reminders   id, family_id, entry_id, text, fire_at, rrule, active, sent_at,
            created_by, created_at
gcal_map    entry_id PK, google_event_id, calendar_id, etag, synced_at     -- этап 7
```

- **Одна таблица `entries` на все четыре типа**, а не четыре таблицы. Поля пересекаются на 80%, а поиск, история и авторство получаются одним кодом. Цена — несколько всегда-пустых колонок у заметок; для двух пользователей это неважно.
- «Кто и когда записал» — `author_id` + `created_at`; «кто и когда закрыл» — `done_by` + `done_at`. **Отдельной таблицы истории правок нет:** это полноценный audit log, а реальная потребность в семье — только «кто завёл» и «кто закрыл», и то и другое уже лежит в `entries`. Заведём, если через полгода окажется, что нужна история изменений текста.
- **Лог разбора LLM — в файл, не в таблицу.** Отдельная таблица с миграцией ради «через месяц посмотреть, где модель ошибается» не окупается; обычный `parse.log` (запрос, ответ, вердикт пользователя) решает ту же задачу нулём кода.
- `source_message_id` позволяет из карточки задачи дать ссылку на исходное сообщение в группе.

## Как бот ведёт себя в общей группе

Работа только в групповом чате даёт две неочевидные проблемы — обе решаются в коде, но их надо заложить сразу.

**1. Privacy mode.** По умолчанию бот в группе видит только команды, ответы на свои сообщения и упоминания `@bot`. Чтобы он мог читать обычные сообщения, в BotFather нужно `/setprivacy → Disable`. **После смены настройки бота обязательно удалить из группы и добавить заново** — иначе изменение не подхватится. Важно понимать: бот в любом случае видит только сообщения, отправленные **после** его добавления — историю чата Bot API не отдаёт, задним числом ничего разобрать нельзя.

**1a. Регистрация семьи — без `/start`.** Отдельной команды-инициализации не будет: любое сообщение из чата, для которого нет строки в `families`, молча создаёт семью с настройками по умолчанию, а любой незнакомый `tg_user_id` — добавляется в `members`. Бот здоровается один раз по апдейту `my_chat_member` (его добавили в группу) и коротко объясняет, как им пользоваться. Так исключается тупик «бота добавили, никто не нажал `/start`, ничего не работает».

**1b. Кто считается членом семьи.** Принимаем допущение явно: **бот доверяет всем участникам чата**. Ролей, прав и модерации нет — если в группу попадёт третий человек, он станет полноправным участником. Это осознанное упрощение: система прав доступа для семейного чата на двоих не нужна, а её отсутствие надо зафиксировать, а не молча подразумевать.

**1c. Правки уже отправленных сообщений не отслеживаются.** Telegram присылает их отдельным апдейтом `edited_message`, и обработчика для него не будет: если человек исправил опечатку после того, как запись создана, она не переедет в базу. Правка делается через кнопку `✏️ Текст` в карточке записи; `source_message_id` даёт ссылку на оригинал.

**1d. Миграция группы в супергруппу.** Если обычная группа станет супергруппой (Telegram делает это автоматически при некоторых действиях), её `chat_id` изменится, и семья «потеряется», так как привязана к `chat_id`. Лечится тремя строками: по полю `migrate_to_chat_id` в апдейте обновить `families.chat_id`. Дешевле сделать сразу, чем разбираться потом, почему бот замолчал.

**2. Бот не должен реагировать на обычную переписку.** Если он будет гнать каждое сообщение в LLM, вы получите и лишние деньги, и ложные задачи из фраз вроде «надо будет как-нибудь съездить». Поэтому два режима, переключаются через `/settings`:

- **`trigger` (по умолчанию, рекомендуется).** Бот реагирует на: команды; ответ (reply) на своё сообщение; упоминание `@bot`; сообщение, начинающееся с `+` (например `+купить молоко завтра к 19`). Обычный разговор игнорируется полностью — ноль вызовов LLM, ноль ложных срабатываний, семейная переписка не уходит наружу.
- ~~**`all`.**~~ **Отменён 28.08.2026** (было: каждое сообщение уходит в дешёвую модель на триаж «это план или болтовня»). Проверка бесплатной моделью вопроса не сняла: у моделей `:free` в OpenRouter лимит 20 запросов/мин и 50 в сутки **глобально на аккаунт** (1000 после разовой покупки кредитов на $10), так что вызов на каждое сообщение выбирал бы суточный лимит и ломал бы заодно префикс `+`. Плюс переписка наружу и ложные срабатывания, которые от цены модели не зависят. У бота один режим — `trigger`. Колонка `families.listen_mode` осталась в схеме мёртвой.

**3. Живая панель дня.** Бот держит в группе одно закреплённое сообщение «📌 Сегодня» и редактирует его при каждом изменении (`editMessageText`), а не плодит новые. То же для активного списка покупок — пункты как inline-кнопки, тап переключает «куплено». Ограничения Telegram (~1 сообщение/сек в чат, редактирования учитываются в общем лимите) на двух пользователях не мешают, но обновления панели стоит дебаунсить на 1–2 секунды.

Два обязательных нюанса, иначе панель будет ломаться на ровном месте:
- **Одновременные тапы.** Оба человека в магазине отмечают пункты — это не редкий случай, а норма. Без защиты два колбэка читают состояние параллельно и один из них теряется. В `panel.py` — `asyncio.Lock` на `family_id` вокруг всего цикла «прочитать → пересобрать текст → отредактировать сообщение».
- **`message is not modified`.** Если оба тапа дали одинаковый итоговый текст, Telegram вернёт ошибку 400. Её нужно ловить (`TelegramBadRequest`) и молча игнорировать — это не сбой.
- **Панель уехала вверх по истории.** Если после панели в чате много сообщений, её никто не увидит. Правило: при обновлении, если после панели было больше N сообщений (или прошло больше суток), — отправить новую и открепить старую, а не редактировать невидимую.

**4. Нативные чек-листы Bot API не используем.** Они появились в Bot API 9.1 (июль 2025), но доступны **только от имени Telegram Business-аккаунта** — обычному боту недоступны. Списки делаем на inline-кнопках.

## Разбор естественного текста

Гибрид, как и просили: свободный текст + кнопки.

**Основной путь — LLM через OpenRouter.** Один вызов `POST /api/v1/chat/completions` с JSON-схемой ответа. В промпт подставляются: текущие дата/время в таймзоне семьи, имена участников, названия существующих списков.

```json
{"intent": "create|query|complete|chitchat",
 "items": [{"kind":"task|note|event|shopping",
            "title":"Купить молоко", "body":null,
            "due_at":"2026-08-27T19:00:00",   // локальное время семьи, не UTC
            "all_day":false, "list":"Продукты", "assignee":"Миша",
            "reminders":[{"at":"2026-08-27T18:00:00"}],
            "confidence":0.93}]}
```
Для повторяющихся — `{"rrule":"FREQ=WEEKLY;BYDAY=TU;BYHOUR=19;BYMINUTE=0"}`; дальше `dateutil.rrule` считает следующее срабатывание. Классические date-парсеры повторяемость не умеют в принципе, это и есть главный аргумент за LLM.

**Карточка подтверждения — обязательна.** Ничего не сохраняется молча:
```
📝 Задача: Купить молоко
📅 завтра, 27 авг, 19:00 · 🔔 за час
[ ✅ Сохранить ] [ 📅 Дата ] [ 🔀 Тип ] [ ✏️ Текст ] [ ❌ Отмена ]
```
**Проверка на дату в прошлом.** Если разобранное время уже прошло (опечатка «12.03» в сентябре, «напомни вчера»), карточка показывает `⚠️ дата в прошлом` и требует явного подтверждения. Иначе тикер честно отработает своей же логикой догонки и выстрелит напоминанием немедленно — сюрприз на пустом месте.

Позже, когда накопится статистика в логе разбора, можно включить автосохранение при `confidence > 0.9` (флаг в `.env`).

**Fallback, когда OpenRouter недоступен или вернул мусор** (интернет отвалился, кончился баланс, модель сломала JSON): `dateparser` с русской локалью и `PREFER_DATES_FROM='future'` тянет простые «завтра в 19», «через 2 часа», «12.03 в 8». Не распозналось — бот предлагает пошаговый мастер `/new` на кнопках. Бот не должен падать или молчать из-за внешнего сервиса.

**Модель.** Задаётся `OPENROUTER_MODEL` в `.env`. Нужна быстрая и дешёвая с приличным русским и поддержкой structured output; при старте — выбрать актуальную из каталога OpenRouter (класс «flash/mini»). ~~При включённом режиме `all` для триажа взять самую дешёвую модель~~ — **неактуально с 28.08.2026**: режим `all` отменён, вторая модель не нужна, настройка `OPENROUTER_MODEL_CHEAP` из конфига удалена.

## Команды и интерфейс

Постоянная нижняя клавиатура: `📅 Сегодня · 🛒 Покупки · ✅ Задачи · 📝 Заметки · ➕ Новое`

| Команда | Что делает |
|---|---|
| `/today`, `/week` | План на день/неделю: время, тип, текст, автор («добавила Аня, вчера в 21:14») |
| `/tasks` | Открытые задачи с постраничной навигацией и кнопкой «Готово» |
| `/notes`, `/find <текст>` | Заметки и поиск по всем записям |
| `/buy` | Активный список покупок как живая панель с чекбоксами |
| `/remind <текст>` | Явное напоминание, минуя разбор типа записи |
| `/new` | Пошаговый мастер на кнопках — путь без LLM |
| `/settings` | Таймзона, время дайджеста, режим прослушивания, автоподтверждение |
| `/family` | Кто в семье, статистика «кто сколько записал» |
| `/export`, `/backup` | Выгрузка в Markdown/CSV и файл БД в чат |

**Утренний дайджест** в `digest_time` (по умолчанию 08:00): события дня с временем, задачи с дедлайном сегодня, просроченное, короткая сводка по покупкам. Если ПК был выключен и время прошло — дайджест уходит при первом запуске с пометкой.

## Этапы

Оценки — в часах активной работы, а не в календарных днях.

| Этап | Что | ~ |
|---|---|---|
| **0. Каркас** | Репозиторий, `.env`, config, Dockerfile/compose, бот отвечает в группе, авторегистрация семьи по `chat_id` и участников, обработка `my_chat_member` и `migrate_to_chat_id` | 3 ч |
| **1. Данные и просмотр** | Модели + первая миграция Alembic, `/new` мастер на кнопках, `/today` `/week` `/tasks` `/notes` `/find` с авторством и временем | 5 ч |
| **2. Напоминания и дайджест** | Тикер, догонка пропущенного, `/remind`, повторяемость через `rrule`, утренний дайджест, закреплённая живая панель дня | 5 ч |
| **3a. LLM-разбор, база** | Клиент OpenRouter с ретраями, JSON-схема, карточка подтверждения (только «Сохранить/Отмена»), режим `trigger` | 5 ч |
| **3b. LLM-разбор, доводка** | Кнопки `📅 Дата` / `🔀 Тип` / `✏️ Текст` — это три отдельных мини-FSM, режим `all`, fallback на `dateparser`, проверка даты в прошлом, лог разбора | 6 ч |
| **4. Покупки** | Списки, живая панель с чекбоксами и блокировкой, «купили» с автором, автоархив закрытых | 3 ч |
| **5. Голос** | ffmpeg-конвертация, облачная расшифровка, показ распознанного текста в карточке | 3 ч |
| **6. Бэкапы и экспорт** | Ежедневный `VACUUM INTO` + отправка файла БД в группу, `/export` в Markdown/CSV | 2 ч |
| **7. Google Календарь** | OAuth один раз, односторонняя синхронизация «бот → общий календарь», `gcal_map` | 5 ч |
| **8. Mini App** | FastAPI + статика, валидация `initData`, календарная сетка и drag-n-drop списков, HTTPS через Cloudflare Tunnel | 30 ч+ |

Этапы 0–4 — работающая система, которой уже можно пользоваться каждый день (около 27 часов). Этапы 5–8 наращиваются поверх без переделки данных.

Про оценку этапа 8 честно: **это грубая прикидка, а не бюджет.** Реальный объём зависит от фронтенд-стека, который ещё не выбран (рекомендую vanilla JS + Telegram WebApp SDK — без сборки и без React, иначе к боту прирастает целый отдельный проект). Первая версия 3-го этапа тоже упрётся в подбор промпта под русские формулировки дат — это итеративная работа, а не разовая.

**Голос (этап 5).** Telegram отдаёт голосовые в OGG/Opus, который принимают не все API, — понадобится `ffmpeg` в образе для конвертации в mp3/wav 16 кГц моно. Делаем в два шага (расшифровка → показ текста → тот же разбор, что и у текста), а не одним вызовом: так видно, что именно бот услышал, и ошибка распознавания не превращается молча в неправильную задачу. Конкретный эндпоинт (мультимодальная модель OpenRouter либо отдельный Whisper-совместимый API) выбрать на этапе реализации по актуальному каталогу.

**Google Календарь (этап 7).** Отдельный общий календарь «Семья», синхронизация **односторонняя** (бот → Google): события и задачи с временем создаются как события, `gcal_map` хранит `event_id` для обновления и удаления. Двустороннюю не делаем — она требует sync-токенов, опроса и разрешения конфликтов, а выгода для двух человек сомнительная. Токен OAuth хранится файлом рядом с БД.

## Сеть и деплой

- **Прокси закладываем сразу.** Доступность `api.telegram.org` из России сейчас нестабильна из-за DPI-фильтрации (по замерам — прямой доступ есть примерно у трети серверов, через прокси — почти у всех). В `.env` — `TELEGRAM_PROXY` и `OPENROUTER_PROXY`; в aiogram задаётся через `AiohttpSession(proxy=...)`. Пустые значения = работаем напрямую. Google API из РФ проверить отдельно на этапе 7.
- **Домашний ПК:** отключить сон/гибернацию (иначе бот просто не работает ночью); автозапуск — задача в Планировщике Windows с триггером «При запуске компьютера» и включённым перезапуском при сбое. Динамический IP не мешает: при polling входящие соединения не нужны.
- **Переезд на VPS** (если домашний ПК окажется ненадёжным): скопировать `data/` и `.env`, `docker compose up -d`. Ничего в коде менять не нужно — ради этого и держим Dockerfile, хотя дома он не используется. Цена решения: образ нужно хотя бы изредка собирать, иначе он тихо протухнет.
- **Бэкап SQLite делать через `VACUUM INTO`,** а не копированием файла: копия работающей базы может оказаться битой.

## Проверка

**Автотесты (pytest) — только на чистой логике,** там, где реально живут баги:
- конвертация «локальное время семьи ↔ UTC», включая переход на летнее время;
- расчёт следующего срабатывания по `rrule`;
- классификация опоздания (вовремя / просрочено / сводка) на подставленном «сейчас»;
- сборка текста дайджеста из фикстуры записей;
- разбор ответа LLM: валидный JSON, JSON в ```-обёртке, мусор → fallback.

Хендлеры aiogram тестами не покрываем — дороже, чем окупается на проекте такого размера.

**Ручной прогон в тестовой группе** (отдельный бот `@..._dev_bot`, отдельный `data/dev.db`):
1. Добавить бота в группу → приветствие; написать что угодно **не нажимая `/start`** → семья создана сама, оба участника видны в `/family`.
2. `+купить молоко завтра к 19` → карточка → «Сохранить» → запись видна в `/today` за завтра с автором.
3. Обычное сообщение «а что там с отпуском» → бот молчит (режим `trigger`).
4. `/remind через 2 минуты позвонить маме` (с `TICK_SECONDS=5` в dev) → напоминание приходит в группу.
5. **Догонка:** остановить контейнер, руками выставить `fire_at` в прошлое, запустить → сообщение приходит с пометкой «было запланировано на …».
6. **Дайджест:** выставить `digest_time` на минуту вперёд и `last_digest_on = NULL` → приходит сводка.
7. `/buy` → добавить 3 пункта → тап по кнопке → пункт зачёркнут, панель отредактирована, а не продублирована.
8. **Гонка:** с двух аккаунтов почти одновременно тапнуть по разным пунктам списка → оба отметились, ошибок в логе нет.
9. **Дата в прошлом:** `+напомни вчера в 19 позвонить маме` → карточка с предупреждением, а не мгновенный выстрел напоминанием.
10. Голосовое «напомни завтра в 9 записать ребёнка к врачу» → показан распознанный текст → карточка → сохранение.
11. Отключить интернет к OpenRouter (неверный ключ) → бот не падает, уходит в `dateparser`, при неудаче предлагает `/new`.
12. `/export` и `/backup` → файлы приходят в чат и открываются.

## Риски и открытые вопросы

1. **Privacy mode в BotFather** — самая частая причина «бот не видит сообщения». После `/setprivacy → Disable` бота нужно удалить из группы и добавить заново.
2. **Приватность.** В режиме `all` вся переписка в группе уходит в OpenRouter. Поэтому по умолчанию `trigger`. Заодно в настройках аккаунта OpenRouter отключить использование запросов для обучения.
3. **Домашний ПК = не 24/7.** Догонка спасает от потери напоминаний, но не от опоздания. Если после месяца использования это будет раздражать — переезд на VPS (91–500 ₽/мес) занимает 10 минут.
4. **Качество LLM-разбора** на «в следующую пятницу», «через пару недель», «каждый второй вторник» заранее неизвестно. Обязательная карточка подтверждения делает ошибку разбора безобидной; лог разбора даст материал для подкрутки промпта. Отдельно проверить, что выбранная модель на OpenRouter вообще нормально держит structured output — поддержка у моделей разная.
5. **Одна таймзона на семью.** Если кто-то уедет в другой пояс — понадобится `members.tz_override`; поле лучше добавить сразу, использовать позже.
6. **Стоимость LLM** при двух пользователях в режиме `trigger` — единицы рублей в месяц; в режиме `all` — заметно больше. Считать по логу разбора.
7. **Группа может стать супергруппой** и сменить `chat_id` — обрабатываем `migrate_to_chat_id` (см. выше). Вероятность низкая, цена обработки — три строки, цена необработки — молчащий бот и непонятно почему.
8. **OAuth-токен Google** лежит файлом в `data/` и переносится вместе с базой — повторная авторизация при переезде на VPS не нужна. Но `.env` и этот файл **не должны попасть в git**; в `.gitignore` — с первого коммита.
9. **Открытый вопрос на этап 8:** Mini App требует публичного HTTPS. С домашнего ПК это Cloudflare Tunnel (бесплатно, но ещё один сервис в автозапуске). Решать, когда дойдём.
