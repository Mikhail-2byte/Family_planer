# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Язык проекта — русский: комментарии, докстринги, тексты бота и документация пишутся по-русски.

## Документы, которые задают работу

`docs/TASKS.md` — пошаговый чеклист реализации: этапы, критерии готовности каждого
пункта и летопись того, как он закрывался. **Прогресс отмечается только там**
(`[ ]` / `[~]` / `[x]`), включая «Текущий этап» и таблицу прогресса. Второй копии
прогресса в проекте нет намеренно: она рассинхронизируется и начинает врать —
именно это случилось с прежней сводкой в шапке этого файла.

Здесь — как проект устроен и что в нём нельзя ломать. Утверждений о том, что уже
сделано, а что нет, в этом файле быть не должно.

## Команды

```bash
# Разработка без Docker (Windows, venv лежит в .venv)
.venv/Scripts/pip install -r requirements-dev.txt
.venv/Scripts/alembic upgrade head      # создаёт data/family.db
.venv/Scripts/python -m bot             # long polling
run.cmd                                 # то же одной командой: миграции + запуск

.venv/Scripts/python -m pytest                                       # все тесты
.venv/Scripts/python -m pytest tests/test_timeutil.py -k week        # часть тестов
.venv/Scripts/ruff check .                                           # линтер
.venv/Scripts/mypy                                                   # проверка типов
.venv/Scripts/alembic revision --autogenerate -m "описание"          # новая миграция
.venv/Scripts/alembic downgrade base                                 # откат

# Docker (боевой запуск на VPS)
docker compose up -d --build
docker compose logs -f
docker compose restart bot      # хватает после правки кода: bot/ и alembic/ смонтированы
```

Всё запускается **из корня проекта**: `bot/config.py` создаёт `Settings()` на импорте,
а `.env` ищется относительно текущей директории. Из другого каталога падает даже
`pytest` — `ValidationError: bot_token Field required`.

Пересборка образа нужна только при изменении `requirements.lock` или `Dockerfile`.
Миграции накатываются автоматически при каждом старте контейнера (`CMD` в `Dockerfile`).

**Проверки, которые обязаны быть зелёными:** `ruff check .`, `mypy`, `pytest`.
Их же гоняет CI (`.github/workflows/ci.yml`) на каждый push и PR. Три вещи,
которые легко нарушить:

- **`ruff format` в проект не заведён и в CI его нет.** Он переформатирует 45
  файлов из 72, не исправив ни одной ошибки: переносы здесь расставлены руками
  и по смыслу. Обоснование целиком — в `pyproject.toml`.
- **`bot/handlers/*` проверяется mypy мягче остального.** Отключены три кода
  (`union-attr`, `arg-type`, `assignment`): aiogram объявляет `call.message`
  и `message.from_user` необязательными, а до хендлера доходят только апдейты,
  прошедшие `IN_GROUP` / `IN_GROUP_CB`. Строгая проверка потребовала бы 54
  `assert`, каждый из которых при осечке стоил бы апдейта. **Остальной код
  проверяется целиком и обязан быть чистым** — именно там нашлось, что
  `sending.edit` принимала разметку шире, чем позволяет `editMessageText`.
- **Ревизии Alembic из проверок исключены почти целиком.** Они — дословный
  вывод автогенерации; приведи их к стилю проекта, и следующая ревизия будет
  переписываться сразу после создания. Уже накатанную ревизию не редактируют
  вовсе: исправленная задним числом миграция расходится с тем, что реально
  выполнилось на боевой базе.

Зависимости в образ ставятся из `requirements.lock` — слепка, снятого с рабочей
машины. `requirements.txt` с диапазонами остаётся для разработки; как обновлять
слепок, написано в его шапке.

## Почему так

Обоснования, пережившие `PLAN.md`. Сам план удалён 28.08.2026, когда почти всё
запланированное было написано, а его разделы про команды и структуру устарели;
файл целиком достаётся из истории git.

**Почему свой цикл-тикер, а не APScheduler.** Очевидный путь — APScheduler с
персистентным `SQLAlchemyJobStore`, одна джоба на напоминание. Отвергнут:
APScheduler 4 до сих пор в альфе и помечен «не для продакшена», а jobstore 3.x
синхронный и конфликтует с async-движком SQLAlchemy — лечится вторым, отдельным
sync-подключением к той же базе. Джобы сериализуются pickle: их не посмотреть
глазами и не починить руками. Главное же — при выключаемом домашнем ПК нужна
догонка пропущенного, а `misfire_grace_time` под это настраивается плохо.
Вместо этого `services/ticker.py`: один `asyncio`-цикл раз в 60 секунд, всё
состояние — обычные строки в SQLite. Рестарт переживается бесплатно, догонка
получается сама собой. Понадобятся сложные cron-правила — APScheduler
добавляется поверх, данные переделывать не придётся.

**Почему SQLite, а не Postgres.** Двое пользователей и сотни записей. Один файл
легко снять (`VACUUM INTO`), увезти на VPS и открыть глазами. Postgres здесь —
лишний процесс и лишняя точка отказа.

**Почему long polling, а не webhook.** Бот живёт на домашнем ПК за NAT, а polling
не требует публичного HTTPS.

**Почему venv дома и Docker только на VPS.** Это один процесс с файлом SQLite —
оркестрировать нечего, а Docker Desktop на Windows тянет WSL2 и ещё одну точку
отказа в автозапуске. `Dockerfile` при этом лежит в репозитории с самого начала:
он окупается при переезде.

**Что отменено и почему.** Оба решения записаны надгробиями, а не стёрты, чтобы
не вернулись как «а давайте ещё»:

- **Режим `all`** — LLM на каждое сообщение чата. Отменён 28.08.2026, разбор
  причины — в инварианте «Режима `all` нет и не будет» ниже.
- **Интеграция с Google Календарём** — отменена владельцем 28.08.2026: не
  отложена, а отменена. Ни OAuth и `token.json`, ни таблицы `gcal_map`, ни
  модуля `services/gcal.py` в проекте не будет. Уцелело от неё только правка и
  удаление сохранённой записи, ставшие этапом 7, — к календарю та дыра
  отношения не имела, она про то, что записанное нельзя было ни переписать, ни
  выбросить.

**Риски, которые остаются открытыми.**

1. **Домашний ПК — не 24/7.** Догонка спасает от потери напоминания, но не от
   опоздания на всю ночь. Станет раздражать — переезд на VPS.
2. **Приватность.** В OpenRouter уходит только явное обращение, но уходит.
   В настройках аккаунта OpenRouter отключено использование запросов для обучения.
3. **Одна таймзона на семью.** Уедет кто-то в другой пояс — понадобится
   `members.tz_override`.
4. **Качество разбора** «в следующую пятницу» или «каждый второй вторник» заранее
   неизвестно. Карточка подтверждения делает ошибку безобидной, а `parse.log`
   даёт материал для подкрутки промпта.
5. **Mini App (этап 8) требует публичного HTTPS** — с домашнего ПК это
   Cloudflare Tunnel, то есть ещё один сервис в автозапуске. Решать, когда дойдём.

## Архитектура

Telegram-бот (aiogram 3.x, long polling) для одного семейного группового чата.
SQLite через SQLAlchemy 2.0 async + aiosqlite, миграции — Alembic.

**Поток апдейта:** `bot/__main__.py` → `FamilyMiddleware` (outer middleware на `dp.update`)
→ роутеры из `bot/handlers/__init__.py`.

`FamilyMiddleware` (`bot/middlewares.py`) — центральное место, через которое проходит всё:
открывает `AsyncSession` на апдейт и кладёт в `data` ключи `session`, `family`, `member`.
Хендлеры получают их как аргументы и **не создают сессии сами**. В личке кладётся только
`session` — `family`/`member` отсутствуют, поэтому у групповых хендлеров с аргументом
`family: Family` обязателен фильтр `IN_GROUP`, иначе aiogram упадёт на резолве аргумента
в приватном чате.

**Права администратора.** До этапа 11 они были украшением: без них панель просто
не закреплялась. С уборкой чата боту нужно право **«удалять сообщения»**
(`can_delete_messages`) — без него уборка молча пропускается со строкой в логе,
остальное работает как прежде.

`bot/filters.py` — `IN_GROUP` (для сообщений) и `IN_GROUP_CB` (для колбэков: у
`CallbackQuery` чат лежит внутри `message`). Групповые роутеры вешают их разом:
`router.message.filter(IN_GROUP)` + `router.callback_query.filter(IN_GROUP_CB)`.
Там же `IN_PRIVATE`: на нём в `admin.py` висит хендлер `private_chat` — ловушка,
отвечающая `PRIVATE_CHAT` на **любое** сообщение в личке. Она стоит в первом
роутере и без других фильтров, поэтому безопасна ровно до тех пор, пока у
`views`, `remind` и `new_entry` на `message` висит `IN_GROUP`: снимете фильтр —
хендлер молча уйдёт в отказ. Страховка — `test_group_routers_never_run_in_private`.

`bot/db/repo.py` — все запросы к БД. Принимает `AsyncSession` первым аргументом и ничего
не знает про aiogram; это делает его тестируемым напрямую (`tests/conftest.py`).

`bot/texts.py` — все русские строки **и единый рендер записей**: `entry_line`
(строка списка), `entry_card` (карточка), `day_header`, `week_header`. Форматировать
записи и даты в хендлерах нельзя — только звать эти функции.

`parse_mode="HTML"` включён по умолчанию, поэтому **любой** текст, введённый человеком,
идёт через `_escape`. Внутри `entry_line`/`entry_card` это уже сделано; для остальных
подстановок в `texts.py` есть функции-обёртки — `search_header`, `search_empty`,
`family_header`, `family_member`, `pong`. Подставлять `.format(...)` в шаблон прямо
из хендлера нельзя: имя участника и название чата задаёт пользователь, и `<` в них
превращает отправку в `TelegramBadRequest: can't parse entities`.

Новый роутер: создать модуль в `bot/handlers/`, объявить `router = Router()`,
добавить в список `routers` в `bot/handlers/__init__.py`. **Порядок в списке значим:**
`views` идёт раньше `new_entry`, иначе команда, набранная посреди `/new`, будет
проглочена FSM-хендлером как текст записи. Обратная сторона этого порядка —
`drop_wizard_state` (`bot/middlewares.py`): внутренний middleware, который вешается
в том же `__init__.py` на все роутеры **кроме мастера** и обрывает зависшее
состояние `/new`, когда сообщение перехватил кто-то другой. Новый роутер, стоящий
раньше `new_entry`, тоже должен его получить.

`entry` (этап 7) стоит между `review` и `new_entry` и получает
`drop_wizard_state` по той же причине, что `review` и `settings`: правка
приходит реплаем на сообщение бота.

`capture` — исключение: он стоит **последним, позади мастера**, и `drop_wizard_state`
ему не нужен. Причина в `IsTrigger`: обращением к боту считается и ответ на его
сообщение, а мастер спрашивает «Что записать?» обычным сообщением — стоя раньше,
`capture` перехватывал бы реплай и крал шаг мастера. Позади мастера этого не
происходит: раньше срабатывает `StateFilter(New)`. Цена — `+…`, набранное посреди
`/new`, получает «сейчас идёт запись через /new» вместо разбора. Обе половины
закреплены тестами в `tests/test_capture_wiring.py`.

Фоновые сервисы (`services/ticker.py`, `services/digest.py`) идут мимо диспетчера,
а значит и мимо `FamilyMiddleware` — они открывают `Session()` сами и берут таймзону
из `families.tz` вручную. `Session` импортируется **по имени на уровне модуля**
(`from bot.db.session import Session`), иначе тест не сможет подменить фабрику
через `monkeypatch.setattr(ticker, "Session", session_maker)`.

Отправка в чат — только через `services/sending.py`: там политика ошибок Telegram
(выгнали → гасим, сломанный текст → сдаёмся сразу, сеть и флуд → ретрай на следующем
тике). Отдельный модуль, потому что политика нужна и тикеру, и дайджесту, а держать
её в `ticker.py` значило бы закольцевать импорты.

`digest.build_day` — единственное место, где день превращается в текст. Его зовёт
утренняя сводка, `/today` и живая панель. Блоков в нём четыре (просрочка, день,
«Дальше», «Без срока»), собирает их общий `_block`, и все они делят один бегущий
бюджет символов — подробности в инвариантах ниже.

`services/sweep.py` — утренняя уборка чата (этап 11). Каждое утро, сразу за
сводкой, бот стирает всё, что лежит в чате выше неё, включая сообщения людей:
день начинается с чистого листа. **Данные при этом не трогаются** — задачи,
события, заметки и покупки остаются в базе, иначе нечего было бы показывать.

Удаляет **диапазоном id, а не списком запомненных сообщений**, и это ключевое
решение. Бот не умеет читать историю чата: удалить он может только то, чей
`message_id` знает, а знает он ровно два — панель дня и панель списка.
Запоминать каждое отправленное значило бы завести middleware на сессию бота и
новую таблицу ради 73 мест отправки. Но `message_id` в чате — сплошная
возрастающая нумерация, а `deleteMessages` молча пропускает несуществующие id,
поэтому достаточно идти подряд. Побочная выгода, которой у уборки по списку не
было бы: сотрутся и сообщения, которых бот **никогда не видел**, — на старте он
делает `delete_webhook(drop_pending_updates=True)`, и всё пришедшее, пока он
лежал, до него не доходит.

Что здесь легко сломать:

- **Водяной знак `families.swept_upto` — это `id сводки минус один`.** Не сама
  сводка: при знаке, равном ей, завтрашний диапазон начнётся выше, и вчерашняя
  сводка не удалится никогда — через месяц в чате тридцать «Доброе утро!».
- **Уборка стоит после `set_last_digest_on`, а не до.** `send_pending` глотает
  исключения `_send_one`; встань уборка раньше и упади — день не пометится, и
  сводка уйдёт заново на следующем тике, и так каждую минуту до полуночи. Та же
  болезнь, что лечили `backup._failed_on` и ветка BROKEN в `panel`.
- **Якорь — id только что отправленной сводки**, другого способа узнать текущий
  максимум id нет. Поэтому порядок физически только «сводка → уборка»; при
  BROKEN и FORBIDDEN якоря нет и уборки не будет — чистить чат, не показав
  сводку, значит стереть день молча.
- **`SWEEP_WINDOW` — потолок сразу двух вещей:** как далеко заглядывать на
  первом запуске и сколько догонять после простоя. `0` выключает уборку.
- **Знак двигается по фактически пройденным пачкам.** Часть сообщений Telegram
  удалять отказывается (служебное о создании супергруппы, слишком старое), и
  знак обязан их перешагнуть — иначе бот долбится в них каждое утро.
- **«Нет прав» и «не удаляется» — разные ошибки, и путать их дорого.** Без
  разделения бот без права `can_delete_messages` делал бы каждое утро одну
  неудачную пачку плюс сотню неудачных одиночных удалений.
- **Уборка сбрасывает `panel_day`, но не `panel_message_id`.** Первое — потому
  что `refresh_stale` считает панель свежей по дню, и панель, перевыпущенная в
  07:00, иначе не вернулась бы весь день. Второе — потому что `refresh_stale`
  пропускает семьи без панели, и результат был бы тот же.
- **`lists.panel_message_id` уборка не трогает вовсе.** `lists.refresh_panel`
  выходит молча при пустом id, и обнуление стоило бы пункта, добавленного
  разбором: он лёг бы в базу, не показавшись в чате. Мёртвый id самолечится.
- **Порядок в `ticker.tick_once` значим:** дайджест раньше `panel.refresh_stale`,
  иначе снесённая панель вернётся только назавтра.
- Импортировать `panel` из `digest` нельзя — `panel` импортирует `digest`.
  Поэтому день панели сбрасывается через `repo`, а не вызовом `panel.schedule`.

`services/panel.py` — закреплённое «📌 Сегодня», которое бот редактирует, а не
шлёт заново. `schedule()` синхронная и откладывает работу на
`PANEL_DEBOUNCE_SECONDS`, отменяя предыдущую задачу семьи, — поэтому **сессию
хендлера внутрь передавать нельзя**: `FamilyMiddleware` закроет её раньше, чем
задача проснётся. `refresh` открывает свою и работает под `asyncio.Lock` на
`family_id`. Тикер зовёт `refresh_stale` — в обычный тик тот не ходит в Telegram
вовсе, только сверяет `families.panel_day` с локальным сегодня.
Редактирование идёт через `sending.edit`, а не через `views.edit_or_ignore`:
второй принимает `CallbackQuery`, и в фоне видимых ошибок быть не должно.

`views.edit_or_ignore` глотает три отказа, и список не случайный: «not
modified» (двое тапнули одну кнопку), «message to edit not found» и «message
can't be edited». Последние два добавила уборка чата: тап по кнопке в
сообщении, которое исчезает в эту же секунду, — теперь **норма**, а не
неожиданность. Раньше такой тап уронил бы хендлер, а упавший апдейт теряется
навсегда. Само действие при этом уже сделано: и `mark_done`, и разбор
незакрытого правят базу до перерисовки, так что теряется картинка, а не запись.

`handlers/lists.py` — **вторая** живая панель, список покупок, и она устроена
намеренно иначе. У неё свой `_locks` с ключом `list_id`; общий с панелью дня
`family_id` заставил бы их отменять работу друг друга. **Дебаунса у неё нет
вовсе:** он существует ради фона, а тап по чекбоксу — интерактив, две секунды
без зачёркивания читаются как «бот завис». Тап к тому же приходит вместе с
`call.message`, который правится прямо в хендлере. Лок при этом обязателен:
без него «прочитать → отрисовать → отредактировать» одного тапа рвётся чужим
тапом, и последней в чат приезжает правка по устаревшему чтению.
Панель списка не закрепляется — видимость ей даёт перевыпуск по
`panel_max_messages`. Тап всё же зовёт `panel.schedule`: в панели дня есть
счётчик покупок, и она обязана узнать об изменении, а вот там дебаунс уместен.

Разбор свободного текста (этап 3a) разложен на три слоя, и смешивать их не надо:

- `services/llm.py` — **транспорт**: OpenRouter, ретраи, «пришёл ли вообще JSON».
  Наружу исключений не выпускает: любой сбой — `None`.
- `services/parsing.py` — **домен**: системный промпт (сегодняшняя дата в tz семьи,
  имена участников, названия списков) и `normalize`, приводящий ответ модели к
  `Item`. Модуль чистый: ни БД, ни aiogram, ни таймзон; **все времена внутри —
  локальные наивные**, перевод в UTC делает хендлер. `normalize` — вторая линия
  обороны: выбранная модель structured outputs не поддерживает, схему держит «на
  слово», поэтому каждое поле проверяется отдельно, а негодный элемент
  выбрасывается, не роняя разбор целиком.
- `handlers/capture.py` — карточка и запись в базу.

Черновики разбора живут в модульном словаре `capture._drafts` с ключом
`(chat_id, message_id)` карточки, **а не в FSM**: ключ FSM — «чат + пользователь»,
и «Сохранить», нажатое не автором фразы, черновика бы не нашло. Словарь ограничен
`MAX_DRAFTS` с вытеснением самого старого, иначе брошенные карточки копятся всё
время работы бота. Как и состояние мастера, черновики не переживают перезапуск.

Правка карточки (этап 3b) устроена так же и по той же причине: тип переключается
кнопками, а дата и текст — **ответом реплаем на саму карточку**; чего именно
ждём, помнит `capture._pending` с тем же ключом. Три места, где легко сломать:

- **Черновик снимается только на «Сохранить» и «Отмена»** (`_finish`). Стоявший
  в 3a `del _drafts` до разбора действия убил бы карточку первым же тапом «Дата».
- **`edit_field` зарегистрирован выше хендлера с `IsTrigger`** — внутри роутера
  порядок значим не меньше, чем между роутерами: реплай на сообщение бота есть
  обращение, и правка ушла бы в модель отдельным запросом.
- **Двоеточие в `callback_data` — разделитель полей aiogram**, поэтому у
  `CaptureCB` отдельное поле `kind`, а не `action="kind:task"`.

`services/parse_log.py` — лог разбора (`data/parse.log`, JSON-строками): по нему
считается стоимость (3b.8) и видно, где ошибается модель. Пишут в него `capture`
и `handlers/voice.py` (своей строкой `event=voice`), и никто больше; исключений
наружу не выпускает — упавшая запись в лог не должна стоить человеку карточки.
В тестах путь уводится в tmp автофикстурой в `conftest.py`, иначе прогон
дописывает сотни строк в боевой лог.

С 29.08.2026 он же **считает суточные обращения к модели** (`calls_today`) и
**ротируется** по `MAX_BYTES`. Счётчик держится в памяти, а из файла читается
один раз за процесс: домашний ПК перезапускается часто, а лимит провайдера от
этого не обнуляется. Ротация — **одно поколение**, и это осознанно: в файле
лежит полный текст человека и полный ответ модели, и хранить семейную
переписку годами ради подкрутки промпта незачем — тот же довод, по которому
ежедневный бэкап не уходит в облако. Та же автофикстура сбрасывает и счётчик:
без этого он течёт между тестами.

Голос (этап 5) — **третий вход в тот же разбор**, и устроен он иначе, чем два
первых. Признаков обращения из `IsTrigger` у голосового нет ни одного: `text`
у него `None`, а подписи Telegram к голосовым не даёт. Поэтому обращением
служит кнопка «🎤 Голосом»: тап кладёт срок в `voice._awaiting` по ключу
`(chat_id, user_id)`, и ближайшее голосовое от того же человека проходит фильтр
`voice._invited`. Голосовое без тапа фильтр не пропускает вовсе — ни одного
внешнего вызова.

Четыре места, где легко сломать:

- **`voice.router` стоит раньше мастера** (между `lists` и `remind`), в отличие
  от `capture`. Шаги `/new` ловят `F.text`, и «🎤 Голосом», нажатое посреди
  мастера, стало бы заголовком записи. `drop_wizard_state` роутеру поэтому
  нужен, как и остальным ранним. Сторож — `test_voice_router_stands_before_the_wizard`.
- **Проверка приглашения — фильтр, а не первая строка хендлера.** Внутри
  хендлера она съедала бы все голосовые чата, и реплай голосом на карточку
  правки перестал бы доходить до `capture.edit_field`.
- **Приглашение не снимается в конце, а забирается в начале.** `_awaiting.pop`
  стоит до первой же паузы на `await`, и хендлер, которому не досталось,
  выходит молча. Апдейты aiogram обрабатывает параллельно: два голосовых подряд
  оба проходят фильтр, и снятие «по успеху» стоило бы двух расшифровок, двух
  вызовов модели и двух карточек на одну фразу. На осечке приглашение
  возвращается с **прежним** сроком, а не с новым.
- **Разбор переиспользуется целиком:** `capture.handle_phrase` — это бывшее
  тело `capture.capture`, и голос зовёт её же. Своего разбора, своих лимитов и
  своей ветки `intent` у голоса нет и заводить их не надо.

Разбор незакрытого (этап 5п) — `services/review.py` (сборка сообщения) и
`handlers/review.py` (кнопки). Утром, следом за сводкой и **вторым
сообщением**, приходит нумерованный список просроченного: закрыть или
перенести. Отдельным сообщением, а не кнопками под сводкой, потому что текст
сводки собирает `digest.build_day` — его же читают `/today` и панель, и
нумерация строк протекла бы в оба.

Что здесь легко сломать:

- **`repo.reschedule_entry` — единственное место в проекте, меняющее `due_at`
  сохранённой записи.** Отдельная функция, а не флаг у `complete_entry`: на
  «уже закрыта → `None`» у той держится `DONE_ALREADY` в `/tasks`. Этап 7 её
  расширил, а не завёл вторую: `due_at=None` снимает срок, `all_day=None`
  означает «не трогать», поэтому вызов из разбора не изменился.
- **Сам перенос с этапа 7 живёт в `services/entries.py`** (`move`, `clear_due`),
  а не в хендлере: он нужен и карточке записи. Вместе с ним переехало гашение
  разовых напоминаний — забыть его слишком легко, а без него перенесённая
  запись выстрелит по прежнему `fire_at`, то есть догонкой в ближайший тик.
- **Перенос меняет день, а не время суток**, и считается в локальном времени
  семьи: наивный `timedelta` поверх UTC уехал бы на час при переводе часов.
  У записи **без срока** времени суток нет вовсе — она становится «на весь
  день»; до этапа 7 такого входа не было, и код звал бы `to_local(None)`.
- **`review.render` возвращает показанные записи, а не все.** По ним строится
  клавиатура — кнопок обязано быть ровно столько, сколько пронумерованных
  строк. Потолок двойной: по числу записей и по символам.
- **`review.router` стоит раньше мастера** (между `settings` и `entry`):
  «другую дату» отвечают реплаем, а реплай на сообщение бота `IsTrigger`
  считает обращением — позади `capture` он уехал бы в модель.
- **Проверка записи есть и в хендлере, и в `repo`, и это не дублирование:**
  `repo` стережёт правку, хендлер — чтение, потому что экран выбора дня
  показывает заголовок записи.
- **При переносе гасятся только разовые напоминания.** Повторяющиеся не
  трогаются: тихо убить серию хуже, чем оставить её как есть.

Карточка сохранённой записи (этап 7) — `handlers/entry.py`. До неё записанное
было неприкосновенно: кнопки `📅 Дата` / `🔀 Тип` / `✏️ Текст` живут в карточке
подтверждения, то есть **до** сохранения, а удаления не было нигде.

Устроена по образцу `handlers/review.py`: **состояния почти нет**, и запись, и
страница, куда возвращает «← Назад», едут прямо в `callback_data`, поэтому
кнопки переживают перезапуск бота. В памяти живёт только `_pending` — ожидание
ответа реплаем.

Что здесь легко сломать:

- **`entry.router` стоит раньше мастера** (между `review` и `new_entry`) и
  получает `drop_wizard_state`. Новый текст и «другую дату» отвечают реплаем, а
  реплай на сообщение бота `IsTrigger` считает обращением — позади `capture`
  он уехал бы в модель отдельным платным запросом.
- **Вход в карточку есть только на страницах `/tasks`, `/notes` и `/events`.**
  В `/today`, `/week` и панели его нет и быть не может: их собирает общий
  `digest.build_day`, и нумерация протекла бы разом в утреннюю сводку и в
  закреплённое сообщение. Ровно поэтому у событий и заведена своя страница.
- **`EntryCB` — отдельный класс с новым префиксом, и поля в нём заводить
  можно.** Вид страницы едет прямо в колбэке, в отличие от `DoneCB`, где его
  приходится добывать из `entry.kind` через `views.view_of`. Без `view_of`
  закрытие события со страницы `/events` перерисовало бы её как `/tasks`.
- **Раскладка списка сменилась на «ряд на запись»** (`[✅ N] [✏️ N]`). Состав
  полей `DoneCB` при этом не тронут: кнопки, уже висящие в чате, обязаны
  работать — они просто не получат «✏️», пока сообщение не перерисуют.
- **Ожидание правки снимается на «← Назад»**, а при неудачном разборе —
  **возвращается**. Обе половины выстраданы в `capture`.
- **Тип записи здесь не меняется**, в отличие от карточки разбора: сменить его
  у сохранённой записи значит выдать или отобрать слот в списке покупок.
- **Исполнитель (29.08.2026) — подпись, а не право.** Кнопка «👤 Кому» пишет
  `entries.assignee_id` — колонку, лежавшую в схеме мёртвой с самой первой
  ревизии. Ролей и прав это не заводит: закрыть и поправить запись по-прежнему
  может любой участник чата (инвариант «ролей и прав нет» в силе). Три места,
  где легко сломать:
  - **Миграции не нужно** — добавлена только связь `Entry.assignee`, а
    `relationship` схему не меняет. Стережёт это `test_schema_matches_the_models`.
  - **`repo.set_assignee` проверяет семью дважды** — и у записи, и у участника.
    Изоляция по `family_id` здесь единственная защита, и без второй проверки id
    из колбэка чужого чата поручил бы нашу задачу постороннему.
  - **`member.id` едет в готовом поле `value`**, вместе со сдвигом дней у
    `'day'`. Новое поле заводить нельзя: кнопки карточки уже разошлись по чату,
    и лишнее поле сделало бы их неразбираемыми — правило то же, что у `DoneCB`.
    В списке поручение показывается только у открытой записи, в карточке — у
    любой: там это часть истории.

Удаление **мягкое** — `repo.archive_entry` ставит `status='archived'`. Что с
ним связано:

- **Физического `DELETE` записи в проекте нет.** Единственные `DELETE` во всём
  `repo.py` — пустышка-семья в `migrate_family_chat_id`.
- **Гасить напоминания не нужно:** `due_reminders` требует `status == 'open'`,
  и удалённая запись замолкает тем же механизмом, что и закрытая.
- **Откат есть, и он не украшение.** Ряд «↩️ Вернуть» дописывается к
  перерисованной странице и живёт до следующей перерисовки. Довод тот же, что у
  `reopen_list`: подтверждение спасает от промаха пальцем, но не от «удалил не
  ту из восьми», а после удаления запись не видна нигде, кроме файла выгрузки.
- **`toggle_bought` обязана отвергать `archived`.** Её ветка «снять галку»
  ловит любой статус, а панелей списка в чате лежит стопка — старые
  перевыпускаются, но не умирают. Без проверки тап по кнопке в любой из них
  воскресил бы удалённый пункт и оживил бы весь список через `reopen_list`.
- **`sync_list_archived` не считает удалённые ни в одном из двух счётчиков.**
  Не вычти их из `total` — список, из которого выбросили всё, уехал бы в
  «🧹 Список закрыт» вместо того, чтобы остаться пустым.

Бэкапы и экспорт (этап 6) — `services/backup.py` и `services/export.py`.

`backup.py` снимает копию через **`VACUUM INTO`, а не копированием файла**: у
базы включён WAL, и часть данных в момент копирования лежит в `family.db-wal`, а
не в `family.db`. Копия работающей базы может оказаться битой, и выяснится это
при восстановлении. Три места, где легко сломать:

- **Отметка «сегодня уже сделано» — сам файл `data/backups/family-<дата>.db`,
  а не колонка в `families`.** Колонка была бы близнецом `last_digest_on` и
  `panel_day`, но бэкап один на всю установку, а не на семью, и отвечать на
  «чьи это сутки» ей было бы нечем. День считается в `TZ_DEFAULT`: бэкап
  машинный, семьи у него нет.
- **Пишем во временное имя и переименовываем.** `VACUUM INTO` отказывается
  писать в существующий файл, а снимок, прерванный под боевым именем, выглядел
  бы готовой копией. Имя временного фиксированное (`snapshot.part`), иначе
  обрывки копились бы навсегда; под маску ротации `family-*.db` оно не подходит.
- **Провал помечает сутки отработанными** (`_failed_on`). Без этого файла дня
  нет — значит «пора делать», — и при полном диске тикер лез бы за снимком
  каждую минуту до полуночи. Та же болезнь, что лечил `panel_day` в 2п.

`export.py` — чистый модуль, как `parsing.py`. **Свой рендер, а не
`texts.entry_line`:** та превращает запись в *сообщение чата* и отдаёт HTML с
экранированием под `parse_mode="HTML"`, а в файле теги — мусор, и `&amp;`
вместо `&` уже порча данных. По той же причине подписи колонок CSV и названия
разделов Markdown лежат в `export.py`, а не в `texts.py`. CSV — `;` и UTF-8
**с BOM**: так его открывает двойным кликом русский Excel; цена — это не
канонический CSV. Потолка у выгрузки нет намеренно (единственный список в
проекте без потолка): она едет файлом, а не сообщением, и обрезанный экспорт
хуже большого.

Третий формат — `export.to_ics`, и он же **всё, что осталось от отменённой
интеграции с Google Календарём**. Отменена была именно интеграция: OAuth,
`token.json`, таблица `gcal_map`, живая синхронизация. Файл `.ics` ничего этого
не требует и запрету не противоречит — его открывает любой календарь, включая
гугловский. Синхронизации здесь нет и не будет: выгрузил и забыл. Что в нём
легко сломать:

- **RFC 5545 считает строку в октетах, а не в символах.** Кириллица занимает
  по два байта, и «перенос по 70 символов» даёт 140 октетов вместо
  разрешённых 75. Режем посимвольно, а границу считаем в байтах (`_fold`) —
  рвать UTF-8 посередине нельзя, получится битый файл.
- **Экранирование идёт в строгом порядке: обратный слэш первым.** Иначе слэш,
  добавленный к запятой, экранируется следующим проходом.
- **Берём только записи со сроком и только не удалённые.** Заметке без срока в
  календаре места нет, а пустая дата делает файл невалидным. Удалённые здесь
  не показываем — в отличие от CSV и Markdown: те задуманы полным слепком базы,
  а календарь это рабочий инструмент. Пустой календарь в чат не уходит вовсе.
- **`ATTENDEE` не используем.** Он требует адреса участника и превращает
  событие в приглашение, которое календарь попытается разослать; поручение
  едет строкой в `DESCRIPTION`.
- **UID обязан быть стабильным** (`<entry_id>@ICS_DOMAIN`), иначе повторная
  выгрузка заводит в календаре дубли вместо обновления записей.

`/backup`, `/export` и `/help` живут в `handlers/admin.py` — новый роутер не
нужен, а ловушка `private_chat` там стоит последней и без фильтров, поэтому
новые хендлеры обязаны быть **выше** неё. `/backup` берёт снимок заново во
временный каталог (ручной снимок не должен вмешиваться в ротацию) и
**отправляет весь файл базы** — это единственное место в проекте, где изоляция
по `family_id` не работает по природе вещей.

`/help` (29.08.2026) — единственное место, где бот объясняет, **когда он
слушает**. Про префикс `+`, реплай и кнопку «🎤 Голосом» узнать было неоткуда:
меню команд перечисляет только команды, а `README.md` в чате никто не читает,
и молчание бота на обычную реплику читалось как поломка.

`services/voice.py` — только транспорт (скачанные байты → текст), по образцу
`llm.py` и с той же политикой ошибок; наружу отдаёт `None` при любом сбое.
Политика **повторов** у них с 29.08.2026 общая — `services/http_retry.py`: до
этого цикл ретраев и константы существовали двумя построчно совпадающими
копиями и разошлись бы молча. Новый исходящий HTTP-клиент обязан брать её
оттуда же, а не заводить третью.
Конвертации нет и `ffmpeg` в проекте нет: Whisper-совместимый эндпоинт
принимает `ogg/opus` Telegram как есть. Смените эндпоинт на мультимодальную
модель OpenRouter — конвертация понадобится снова (там надёжны только
`wav`/`mp3`), и вернётся отменённый пункт 5.1.

## Инварианты, которые легко нарушить

- **Никакого `/start`.** Семья и участники заводятся сами по первому же апдейту из группы
  (`get_or_create_family` / `get_or_create_member`). Не добавлять команду-инициализацию.
  Кнопка START в личке шлёт `/start`, и он попадает в общую ловушку `private_chat`,
  которая отвечает «работаю только в группе» и ничего не инициализирует.
- **Всё время в БД — naive UTC** (SQLite таймзон не знает). Таймзона семьи (`Family.tz`)
  применяется только на границе ввода и вывода — через `bot/services/timeutil.py`.
  Модуль чистый: ни БД, ни aiogram внутри.
- **У повторяющегося напоминания отработку помечает `fire_at`, а не `sent_at`.**
  Разовое закрывается через `sent_at = now`; повторяющееся получает новый `fire_at`
  в будущем, а `sent_at` остаётся пустым навсегда. Благодаря этому выборка тикера
  одна на оба случая. Не «чинить», проставляя `sent_at` повторяющимся, — оно
  замолчит навсегда.
- **`rrule` считается в локальном времени семьи**, якорь — текущий `fire_at`
  напоминания. Взять за якорь «сейчас» значит потерять время суток серии, а считать
  в UTC — уехать на час при переводе часов.
- **`bot/db/sqlite.py` импортируется ради побочного эффекта** (`# noqa: F401` в `repo.py`):
  он вешает на класс `Engine` регистрацию SQLite-функции `lower_unicode`. Встроенный
  `lower()` умеет только ASCII, без этого поиск по кириллице не работает. Там же
  выставляются `PRAGMA journal_mode=WAL`, `busy_timeout` и `foreign_keys=ON` —
  без первых двух тикер и хендлер, пишущие одновременно, ловят `database is
  locked`, а без третьего все `ForeignKey` в `models.py` остаются декларацией:
  SQLite по умолчанию их **не проверяет**. Симптом второго до сих пор виден в
  тикере — «осиротевшие напоминания — данные из прошлой жизни». PRAGMA не
  глобальная, а на соединение, поэтому и висит на событии `connect`.
  Не удалять «неиспользуемый» импорт.
- **`allowed_updates` вычисляется из зарегистрированных хендлеров**
  (`dp.resolve_used_update_types()`). Новый тип апдейта не начнёт приходить, пока на него
  нет хендлера, — симптом «Telegram молчит» без единой ошибки в логе.
- **На старте `delete_webhook(drop_pending_updates=True)`** — сообщения, пришедшие пока
  бот лежал, теряются намеренно. Догонка (этап 2) восстанавливает **напоминания из БД**,
  а не пропущенные сообщения.
- **FSM-состояния живут в памяти** (`MemoryStorage` по умолчанию): рестарт бота обрывает
  незавершённый `/new`. Осознанно; менять — только вместе с выбором хранилища.
- **Ролей и прав нет.** Бот доверяет всем участникам чата — осознанное упрощение.
  Изоляция только по `family_id`: колбэк из чужого чата не должен трогать чужую запись
  (см. `complete_entry`).
- **`edited_message` намеренно не обрабатывается.** Правка записи — через кнопку в карточке.
- **Миграция группы в супергруппу** меняет `chat_id`; она обрабатывается в middleware
  (`migrate_to_chat_id` / `migrate_from_chat_id`) — не ломать эту ветку.
  Слепого `UPDATE ... WHERE chat_id = old` тут **недостаточно**, и это выяснилось
  боевым переездом: Telegram шлёт разом служебное сообщение о переезде и апдейт о
  боте в новом чате, aiogram обрабатывает их параллельно, и автосоздание семьи
  успевает занять новый `chat_id` первым. `migrate_family_chat_id` поэтому
  удаляет пустышку и переводит настоящую семью, а пустышку **с данными** не
  трогает вовсе. Цена ошибки здесь необычно высока — см. следующий пункт.
- **Апдейт, обработка которого упала исключением, теряется навсегда.** Offset
  Telegram сдвигается независимо от исхода, повторной доставки нет. Для
  повторяющихся событий это лишь пропуск, а для одноразовых — переезда в
  супергруппу, добавления бота в чат — второго шанса не будет, и чинить придётся
  руками в базе. Обработчики таких событий должны быть устойчивы к гонкам, а не
  рассчитывать на ретрай.
- **Прокси заложены с этапа 0**: `TELEGRAM_PROXY`, `OPENROUTER_PROXY` и `STT_PROXY`,
  пустое значение = ходим напрямую. Все новые исходящие HTTP-клиенты должны
  уважать свой прокси.
  Прокси **обязателен** там, где `api.telegram.org` заблокирован: `aiohttp`, на
  котором работает aiogram, переменные `HTTP_PROXY`/`HTTPS_PROXY` игнорирует
  (`trust_env` по умолчанию выключен), поэтому системный прокси сам собой не
  подхватится — в отличие от `httpx`, который его уважает. Отсюда обманчивая
  картина: ручная проверка токена через `httpx` проходит, а бот молчит.
  Для `AiohttpSession(proxy=...)` нужен пакет `aiohttp-socks` (в
  `requirements.txt`) — без него aiogram отказывается создавать сессию вовсе.
- **Панель пишется в БД до закрепления.** `pin_chat_message` может не пройти —
  прав админа может не быть, — и тогда панель обязана остаться незакреплённой,
  а не выпускаться заново на каждой правке. Ошибки закрепления глотаются целиком.
- **«message is not modified» для панели — это `OK`, а не ошибка.** Так
  отсеиваются холостые перерисовки. Поэтому в текст панели нельзя класть ничего
  изменчивого (времени обновления, счётчиков): каждая правка станет настоящей
  и будет тратить лимит чата.
- **Ничего не сохраняется молча.** Разбор текста всегда даёт карточку подтверждения.
- **`☐` и `✅` — это состояние, всё остальное — вид записи** (этап 10).
  `texts.STATE_OPEN` / `STATE_DONE` стоят первым символом строки в каждом списке,
  значок вида (`KIND_ICONS`) — вторым. До этапа 10 значок был один и совмещал оба
  смысла: открытая задача рисовалась как «✅», закрытая как «✔️», и на экране это
  читалось наоборот — первое, о чём спросил владелец после живого прогона. Тот же
  «✅» означал ещё и кнопку закрытия, кнопку клавиатуры, «куплено» и «Сохранить».
  Заводя новый значок, проверьте, что он не занят: `📌` — у `PANEL_HEADER`,
  `🗑` — у удаления, `🗄` — у закрытия заметки.
- **Заметка не бывает просроченной.** `repo.overdue_entries` исключает
  `kind='note'`: заметка — то, что надо **помнить**, а не сделать. Фильтр стоит в
  `repo`, а не в `digest`, потому что ту же выборку читает
  `services/review.overdue`, и списки сводки и разбора обязаны совпадать. Цена
  решения: заметка с прошедшим сроком не видна нигде, кроме `/notes`, — и это её
  дом. Кнопка закрытия у заметки подписана «🗄», а не «✅» (`DONE_LABEL_BY_VIEW`);
  `DoneCB` при этом не тронут — меняется только подпись.
- **Удаление записи мягкое и одностороннее по видимости.** `status='archived'`
  отсеивается во всех выборках, кроме двух, и обе — решение, а не забытый
  фильтр: `all_entries` (выгрузка обязана помнить всё; это единственное место,
  где удалённое видно, и `export.py` обязан его пометить) и
  `entry_counts_by_author` (`/family` меряет вклад человека, а не остаток дел).
  Заводите новую выборку по `entries` — решите про `ARCHIVED` явно.
- **Режима `all` нет и не будет.** Бот разбирает только явное обращение
  (`filters.IsTrigger`: префикс `+`, реплай на его сообщение, `@упоминание`).
  Отменён 28.08.2026: у моделей `:free` лимит 50 запросов в сутки **на аккаунт**,
  и вызов на каждое сообщение чата выбил бы его, сломав заодно и `+`. Колонка
  `families.listen_mode` осталась в базе мёртвой (удаление = пересборка таблицы
  `families` ради нуля выгоды), значение всегда `trigger`. На экран `/settings`
  её не возвращать: настройка, которую нельзя изменить, обещает переключатель —
  это стережёт `test_settings_does_not_promise_a_listening_mode`.
- **Закрыть запись умеет ровно один колбэк — `DoneCB` → `views.mark_done`.**
  Кнопка есть в `/tasks`, `/notes` и (с этапа 7) `/events`; пункты списка
  покупок закрываются своим `toggle_bought`. Покупка **вне списка** по-прежнему
  не закрывается ничем, но её и не должно существовать: `list_id` обязателен
  (см. ниже).
- **Вид страницы в `mark_done` берётся из `entry.kind` через `views.view_of`,
  а не из колбэка.** Поле в `DoneCB` завести нельзя: у кнопок, уже висящих в
  чате, `callback_data` вида `done:42:0`, и лишнее поле сделало бы их
  неразбираемыми — тап по старому списку молча перестал бы работать. Правило
  общее: **менять состав полей у `CallbackData`, которые уже ушли в чат,
  нельзя**. Заводить поля в **новом** классе (`EntryCB`) при этом можно и нужно
  — там вид страницы едет явно.
- **`complete_entry` закрывает необратимо, `toggle_bought` — переключает.** Это
  разные функции, и сливать их нельзя: на «уже закрыта → `None`» у первой
  держится `DONE_ALREADY` в `/tasks`, а пункту списка повторный тап обязан
  снимать галку — иначе промах пальцем в магазине не откатить. Снятие обнуляет
  `done_at` и `done_by`, иначе «купила Аня» останется на непокупленном пункте.
- **`sync_list_archived` закрывает список, но никогда не открывает.** Открывает
  только `reopen_list`, и только когда тап **снял** галку. Симметричный
  пересчёт выглядит проще и был написан первым, но стирал явное закрытие:
  список, закрытый кнопкой «🧹 Список закрыт» с недокупленным остатком, оживал
  от первого же тапа по этому остатку. Обратный ход нужен ради мис-тапа —
  автоархив без него делает промах пальцем в магазине неисправимым. Пустой
  список закрытым не считается: иначе только что созданный сразу уезжал бы в
  архив. С этапа 10 отмена мис-тапа стоит **двух** тапов, а не одного: панель
  закрытого списка схлопывается, чекбоксов на ней нет, и сначала жмут «↩️
  Вернуть в работу». Размен принят сознательно — тридцать мёртвых строк висят
  каждый день, а промах случается редко.
- **`reopen_list` отказывает, если у семьи уже открыт другой список** (этап 10),
  и это инвариант данных: открытый список у семьи ровно один. Панелей списка в
  чате лежит стопка, старые перевыпускаются, но не умирают, — и тап по галке в
  старой оживлял список, у которого уже был преемник. Дальше тот пропадал
  **отовсюду**: `active_list` берёт последний по id, то есть новый, а
  `closed_list_with_leftovers` требует `archived IS TRUE` — разархивированный не
  находился и там. Проверка стоит в `repo`, а не в хендлере: зовущих двое.
- **Закрытый список схлопывается, но остаток остаётся на глазах.** Панель
  закрытого — итог «куплено N из M», дата и ненумерованный список
  недокупленного (`texts.closed_panel`). Спрятать остаток за кнопкой «Вернуть»
  нельзя: та отказывает, когда уже открыт новый список, и недокупленное стало бы
  недостижимо — ровно ту дыру ревизия уже закрывала однажды. Строки остатка не
  нумерованы намеренно: кнопок под ними нет, а номер обещает тап. Дата печатается
  через `day_stamp`, а не «вчера/сегодня»: относительная метка меняется на
  полуночи, и панель начала бы переписываться сама по себе.
- **Голый `/buy` не создаёт строку в `lists`.** `repo._family_is_empty` считает
  списки, и семья со строкой в `lists` перестаёт быть пустышкой — а на этой
  проверке держится переезд в супергруппу, где второго шанса не будет.
- **Любая запись `kind='shopping'` обязана получить `list_id`.** Иначе её не
  видно нигде: `/buy` смотрит на `list_id`, день и «Просрочено» — на `due_at`
  (а у покупки его чаще нет), `/tasks` и `/notes` — на `kind`. Такая запись
  находится только через `/find`, то есть теряется сразу после «Записал.».
  Слот даёт `repo.shopping_slot`; звать его обязаны **все** пути создания —
  сейчас это мастер `/new` и `capture._save`. Заведёте третий — не забудьте.
  Там же второй долг: после сохранения покупки звать `lists.refresh_panel`,
  иначе пункт есть в базе, а живая панель списка показывает старое до
  ближайшего тапа. `panel.schedule` этого не делает — она про панель дня.
- **Блок «Без срока» в сводке дня обязан фильтровать виды белым списком.**
  `repo.undated_entries` берёт `kind IN ('task','note')`, а не «всё, кроме
  shopping». Разница не косметическая: пункт списка покупок — это ровно
  `status='open'` без `due_at`, то есть он подходит под выборку «без срока» по
  всем признакам, и с чёрным списком следующий заведённый вид протёк бы в сводку
  молча. Тот же довод у `DAY_BLOCK_KINDS` для блока «Дальше».
- **Блоки сводки дня тратят один бегущий бюджет символов, и порядок значим.**
  Просрочка, день, «Дальше», «Без срока» — каждый следующий получает остаток
  (`digest.build_day`). Поэтому обрезается справочный хвост, а не сегодняшние
  дела. Добавляете блок — не забудьте вычесть бюджет **и после предыдущего**: до
  этапа 10 день был последним, и после него не вычиталось ничего.
  `texts.DAY_RESERVE` тут ни при чём — это запас под рамки, которых сборщик дня
  не видит. Пустоту блока определяет `digest._block`: `entry_lines` при нехватке
  бюджета отдаёт не пустой список, а `["…и ещё N"]`, и наивная проверка нарисует
  заголовок над одним счётчиком.
- **`has_content` решает, будить или нет, а не слать или нет** (этап 11). До
  уборки чата он запирал отправку: пустой день молчал. Теперь сводка уходит
  каждое утро — молчание оставило бы человека с вычищенным чатом без единого
  объяснения, куда всё делось, — а флаг ушёл в `silent`: «на сегодня ничего не
  запланировано» приходит без звука. Считают его по-прежнему **только просрочка
  и сам день**: ни «Дальше», ни «Без срока», ни счётчик покупок на него не
  влияют, иначе тихих утр не осталось бы вовсе.
- **У пунктов списка нет `due_at`, и на этом держится их отсутствие в дне.**
  `entries_for_range` и `overdue_entries` требуют непустого `due_at`, поэтому
  покупки не протекают в `/today`, `/week`, дайджест и панель дня. Появится у
  них срок — потекут все четыре разом.
- **4096 символов Telegram — отказ, а не обрезка.** Любое сообщение, длину которого
  задаёт не разработчик, обязано иметь потолок: списки — через `MAX_*_ITEMS`, разбор
  LLM — через `texts.MESSAGE_LIMIT`. Резать готовый текст посередине нельзя: обрыв
  внутри HTML-тега даёт `can't parse entities`, то есть потерю всего сообщения, —
  отбрасывать надо целыми блоками (`texts.join_under_limit`). И разница, которую
  легко потерять: **карточку подтверждения обрезать нельзя вообще** — кнопкой
  подтвердили бы невидимое; её слишком длинный вариант отклоняется целиком, до
  сохранения. Подтверждение после сохранения обрезать можно: записи уже в базе.
- **Потолков всегда два: по числу записей и по символам.** Ревизия 29.08.2026
  нашла, что второго не было почти нигде: `MAX_DAY_ITEMS`, `MAX_WEEK_ITEMS` и
  `SEARCH_LIMIT` считают записи, а длину заголовка задаёт человек — `String(500)`
  на запись даёт 7500 символов при пятнадцати строках. Символьный потолок
  живёт в `texts.entry_lines(budget=...)`; `digest.build_day` тратит бюджет по
  ходу сборки и оставляет `texts.DAY_RESERVE` под рамки, в которые его текст
  завернут снаружи (заголовок дайджеста, рамка панели). Единственный образец
  «как надо» до этого был один — `services/review.render`.
- **Дата от модели проверяется по границам, и на обоих путях разбора.**
  `0001-01-01` модель отдаёт вместо «даты нет», а перевод такой даты в UTC даёт
  `OverflowError` — падение хендлера ещё до карточки. Границы —
  `parsing.MIN_YEAR` / `MAX_YEAR`, и `nlp_fallback.parse_when` берёт их оттуда
  же: `dateparser` уезжает в 2110 год не реже, чем модель в первый.
- **`dateparser` выдумывает время, и это лечится в одном месте.** Неназванное
  время он берёт из «сейчас»: «завтра» в 14:37 даёт «завтра в 14:37», и человек
  унесёт выдумку в базу, подтвердив карточку кнопкой. Решает `nlp_fallback.as_due`
  — **общая** функция, звать её обязаны все, кто трогает результат `parse_when`.
  Правило родилось в `capture._fallback`, а правку даты ответом на карточку
  завели позже и про него забыли; расхождение прожило до ревизии.
- **Ожидание внешнего вызова ограничено сверху.** `http_retry.TOTAL_BUDGET`
  накрывает весь цикл повторов, а не только паузы: `ATTEMPTS × TIMEOUT` давало
  186 секунд на вызов и до шести минут на голосовое (расшифровка плюс модель).
  Политика повторов одна на `llm.py` и `voice.py` — до выноса она существовала
  двумя построчно совпадающими копиями и разошлась бы молча.
- **Суточный лимит модели считаем сами.** У бесплатного тира OpenRouter он
  на аккаунт, а не на ключ; провайдер о приближении не предупреждает, а просто
  начинает отвечать 429 — и разбор молча деградирует до `dateparser`. Счётчик
  живёт в `parse_log.calls_today()` (по строкам `event=parse, via=llm`, сутки
  по UTC — там же граница у провайдера), порог — `LLM_DAILY_LIMIT`, `0`
  выключает проверку. Голос не считается: у Groq своя квота, ради этого он и
  разведён с OpenRouter.
- **Ежедневный бэкап — только на диск.** В чат он сам не уходит: копия «вне
  машины» берётся руками через `/backup`. Решение владельца 28.08.2026 — база
  семьи не должна оседать в облаке Telegram навсегда, удалить её оттуда нельзя.
  Цена принята: пожар и смерть диска остаются потерей данных.
- `.env`, `data/`, `parse.log` — никогда в git.

## Данные

Пять таблиц (`bot/db/models.py`): `families`, `members`, `lists`, `entries`, `reminders`.
`entries` — одна таблица на все типы записей, тип в поле `kind`
(`task` / `note` / `event` / `shopping`).

У `Entry` три внешних ключа на `members` (`author_id`, `done_by`, `assignee_id`),
поэтому связи `author` / `closer` / `assignee` объявлены с явным `foreign_keys`
и `lazy="selectin"` — иначе async-сессия упадёт на ленивой подгрузке автора при
рендере строки. На `lazy="selectin"` вдобавок молча держится `services/export.py`:
модуль чистый, сессии у него нет, а имена авторов он берёт через связи —
переключение на `select` дало бы там `MissingGreenlet`.

`alembic/env.py` берёт URL из `bot.config.settings.db_url`, а не из `alembic.ini` —
один источник правды. Автогенерация настроена с `render_as_batch=True` (требование SQLite).

## Тесты

`pyproject.toml`, секция `[tool.pytest.ini_options]`: `asyncio_mode = strict` — каждому
async-тесту нужен `@pytest.mark.asyncio`, async-фикстуре — `@pytest_asyncio.fixture`.
Общие фикстуры лежат в `tests/conftest.py`:
`session_maker` (фабрика на общей БД в памяти), `session`, `family`, `anya`.
`session_maker` нужен там, где сессию открывает не тест, а сам код: например,
`FamilyMiddleware` зовёт `Session()` сам, и в тесте его подменяют через `monkeypatch`.

**Файлов регрессий два, и они не взаимозаменяемы.**
`tests/test_regressions.py` — ревизия этапов 0–1, `tests/test_regressions_audit.py`
— ревизия этапов 0–7 (29.08.2026). Смешивать поводы не надо: через полгода не
понять, какой тест какой баг стережёт. Правило у обоих одно: **тест обязан
падать на коде «до правки»**; если он станет зелёным при откате фикса, он
потерял смысл. Проверялось прогоном на `git worktree` с прежним кодом — 17 из 17
красные.

Схема в тестах строится через `Base.metadata.create_all` на `sqlite+aiosqlite:///:memory:`,
и **миграции в этом не участвуют** — так быстрее и так задумано. Раньше ценой
этого было «правка модели без новой ревизии даёт зелёные тесты и падение на
боевом старте», и держалось оно на памяти разработчика. Теперь память заменена
проверкой: `tests/test_migrations.py` гоняет `upgrade head` → `downgrade base` на
временной файловой БД и сверяет схему с `models.py` через `compare_metadata`.
Покраснел — не чинить сравнение, а делать `alembic revision --autogenerate`.

## Внешние зависимости и настройка

`BOT_TOKEN` от @BotFather обязателен. В BotFather нужно `/setprivacy → Disable`,
**после чего удалить бота из группы и добавить заново** — иначе он не увидит обычных
сообщений. Историю чата до своего добавления бот не видит в принципе.

LLM-разбор (этап 3a) идёт через OpenRouter; при пустом `OPENROUTER_KEY` бот должен
работать без него. Полный список переменных — в `.env.example`.
